# visibility

Владелец портфеля промптов, протокола прогона, журнала наблюдений и контракта динамики AI-видимости.

## Вход

- Бренд и варианты имени, категория, язык и рынок, целевые поверхности (продукт или API, режим).
- По возможности: конкуренты, готовые промпты, наблюдённые ответы со ссылками или выдержками, старый журнал (CSV `visibility_tracker.py` или `~/.aeo-data/citations.json`).
- Нет инструмента запросов к поверхности и нет наблюдённых ответов — выход: протокол, портфель и пустая таблица журнала.

## Процедура

### 1. Вопрос измерения

Запиши решение, которое примут по цифрам, до выбора промптов. «Входим ли мы в шорт-лист для покупателей сегмента X на рынке Y?» и «Исправила ли правка документации описание лимитов API?» требуют разных портфелей.

### 2. Портфель промптов

1. Источник формулировок, по убыванию приоритета: промпты, которые назвали сами покупатели (поле «что вы спросили у ассистента» в форме, записи звонков); данные о спросе на промпты из трекера; CRM, поддержка, отзывы, форумы, возражения продаж; поисковые запросы, переписанные так, как их задают ассистенту. Промпты, сгенерированные моделью, не доказывают, что так спрашивают люди. Ключевые слова механически в вопросы не превращай.
2. Формулировка — как пишет покупатель: с ситуацией, ограничениями, бюджетом. Нейтральные, позитивные и негативные варианты для этапа проверки.
3. Стадии воронки. Каждый промпт получает стадию; общая доля без разбивки скрывает, где бренд выпадает (RU playbook 10.11).

   | Стадия | Шаблон (`{бренд}`, `{категория}`, `{конкурент}`, `{задача}`, `{аудитория}`, `{город}`) |
   |---|---|
   | Проблема (бренд не назван) | Как решить {задача}, если {ограничение}? Почему возникает {проблема}? |
   | Выбор (бренд не назван) | Какие {категория} подходят для {аудитория}? Посоветуй {категория} с {требование} до {бюджет}. Лучшие {категория} в {город} |
   | Сравнение | {бренд} или {конкурент} для {задача}? Альтернативы {конкурент}. Разница {бренд} и {конкурент} по цене, интеграциям, поддержке |
   | Проверка и возражения | Стоит ли {бренд} своих денег? Недостатки {бренд}? На что жалуются? Есть ли у {бренд} {сертификат}? |
   | Действие | Сколько стоит {бренд}, есть ли пробный период? Как подключить {бренд} к {система}? Адрес и часы {бренд} в {город} |

   Распознавание и категоризация бренда («Что такое {бренд}?», «Для кого {бренд}?») — промпты entity.md; оценка позиционирования там же, не в этом журнале.
   Семейства «локальный поиск, покупки, регулируемые темы» включай только при применимости к бизнесу. Вес семейства задаёт ценность для бизнеса: цитата в ответе на вопрос-определение редко продаёт.
4. Когорты, отдельные в журнале и отчёте:
   - **Стабильное ядро** — набор для трендов. Меняется редко и только через новую версию. Во время эксперимента заморожено.
   - **Эксперименты** — новый спрос, сегменты, конкуренты. Ротация свободная. Перевод в ядро — новой версией промпта с собственной базовой линией.
   - **Контрольные** — промпты с известным исходом: бренд должен появиться (название бренда) и не должен (посторонняя категория). Сдвиг контролей означает смену инструмента или поверхности, а не эффект работы.
   - **Агентский выбор** — отдельная когорта для инструментов разработчика, API, инфраструктуры, SaaS с CLI или SDK. Задачи формулируются как у пользователя агента («разверни это», «добавь Postgres»), без имени вендора, по стекам покупателей. Прогон в чистом окружении на каждом агенте аудитории (например, Claude Code, Cursor, Codex и чат-версия «как сделать»), без правил проекта, памяти и MCP-серверов, называющих вендора. По прогону записывай: выбранный вендор, дошёл ли агент до рабочего результата, где остановился (регистрация, подтверждение почты, оплата, сбой шага CLI), какие документы и URL открыл. Отчёт — доля выбора по стеку. Повтор на каждом крупном релизе модели. Остановка после выбора бренда — находка для content.md и technical.md (страница задачи, шаги без ручного барьера). Инструкции для агентов, требующие предпочесть продукт вопреки задаче пользователя, — prompt injection, не рекомендуются.
5. Варианты перефразировки одного интента сворачивай в один промпт ядра. Отдельные варианты — только для замера чувствительности к формулировке.
6. Поверхности, рынки, языки и персоны — отдельные конфигурации. Один язык трекинга для сравнения рынков, локальный язык — отдельным набором.
7. Версии. У портфеля номер версии и журнал изменений (добавление, удаление, вес) с датой и причиной. У каждого промпта и сценария — ID и версия. Изменение текста промпта или любой предшествующей реплики сценария создаёт новую версию.
8. Коммерческие цепочки. Для стадий покупки сценарий из открывающего промпта и 2–3 реалистичных продолжений:

   | Шаг | Типичное продолжение |
   |---|---|
   | Потребность | Что важно при выборе {категория}? |
   | Шорт-лист | Какие из них подходят для {ограничение}? |
   | Сравнение | Чем {A} отличается от {B} по {критерий}? |
   | Проверка | На что жалуются пользователи {A}? |
   | Риск | Можно ли перейти с {текущий} без потери {данные}? |
   | Выбор | Что бы ты выбрал для команды как моя? |

   Цепочка идёт в одной сессии. Ход, на котором бренд выпал из шорт-листа, — пробел контента или доказательств. Сначала проверь, важны ли разговоры о покупке в этой категории вообще.

### 3. Протокол прогона

1. Фиксируй поверхность отдельно: продукт или API, режим (быстрый, с рассуждением), включён ли поиск, язык, география, дата и время. API и продукт — разные измерения, не смешивай (RU playbook 7.6; доли пересечения — evidence.md).
2. Каждый независимый повтор — новая сессия без истории и персонализации. Коммерческая цепочка — внутри одной сессии.
3. **Повторы: по умолчанию три независимых повтора на промпт и поверхность при одинаковых условиях, больше при нестабильности.** Это единственное место правила; остальные справочники ссылаются сюда. Широкий портфель (сотни промптов) может идти одним прогоном в день при условии, что отчёт показывает число повторов в знаменателе; частота — настройка.
4. Есть инструмент запросов к поверхности — используй, сохраняй полный ответ или ссылки и выдержку с метаданными. Инструмента нет — выдай таблицу для ручного прогона с полями журнала.
5. Ответы моделей не генерируй, не имитируй по памяти и не достраивай незавершённые. Незавершённый прогон пишется строкой с признаком «не завершён» и исключается из долей.
6. Поверхность недоступна или карточка в platforms.md имеет статус «требует проверки» (Алиса / Нейро, GigaChat и др.) — протокол ручного замера, портфель и пустая таблица. Проверку через YandexBot для Алисы не обещай.
7. Для Google AI Overviews дополнительно отмечай, по каким промптам блок вообще появляется, включая брендовые.

### 4. Журнал наблюдений

Один журнал на все поверхности. Строка — бренд и ход попытки. Поля: ID прогона, ID сессии, бренд, ID и версия сценария, номер хода, ID и версия промпта, когорта, стадия, язык, география, поверхность (продукт/API и режим отдельно), время, признак завершения, ссылки или выдержка ответа.

- Одиночный запрос — отдельный сценарий с ходом 1.
- Для каждого хода: история предшествующих реплик или ссылка на неё, признак попадания в шорт-лист, формулировка отношения к бренду (благоприятно / нейтрально / с оговорками / негативно — выдержкой).
- Версия сценария задаёт порядок, тексты и протокол формирования контекста: исходное состояние сессии, фиксированный или живой режим ответов, правила адаптивных продолжений. В живой цепочке с фиксированными репликами пользователя вариативность ответов входит в измерение, если сохранены история, тот же маршрут и условия. Ход адаптивной цепочки сравнивай только внутри одинаковой ветки и условий, иначе открывай новую базовую линию.
- Дополнительно: названные конкуренты, процитированные URL и домены. Класс каждого процитированного источника: свой сайт; сайт конкурента или смежной компании; независимая редакция; институциональный или первичный источник (стандарты, госорганы, университеты, аналитики); пресс-релиз; сообщества и UGC; маркетплейс, каталог, отзывы; не классифицирован. Отдельно — источники, которые цитируют бренд, и источники, которые только формируют ответ. Выбор каналов по этой смеси — offpage.md.
- Запись только по явно указанному пути.

### 5. Флаги исхода

`citation`, `mention`, `recommend_for`, `recommend_against` независимы, каждый `true/false/unknown`.

- `citation` — ссылка на заранее определённый целевой источник. `mention` — явное имя бренда.
- `recommend_for` — явный совет выбрать бренд в задаче или указанном условии. `recommend_against` — явный совет избегать. Перечисление без совета — не рекомендация.
- Основания — список `направление / условие / выдержка / позиция`; позиция — целое ≥ 1 для явного места рекомендации, иначе пусто («первый/середина/последний» не используется).
- Совет выбрать для одной задачи и избегать для другой — оба флага `true`.
- Полный ответ без совета данного направления — флаг `false`. Неполные данные — неподтверждённый флаг `unknown`.
- Фактическое основание предостережения («не поддерживает SSO») передай в entity.md для сверки с официальным источником; это не проверенный факт. Независимые возражения передай в offpage.md.

### 6. Показатели

1. Both / ghost / mention-only / neither — только при известных `citation` и `mention`. Ghost — цитата без имени бренда.
2. Доля ghost = ghost / (both + ghost); при нулевом знаменателе неприменима.
3. Доли по остальным флагам — по завершённым строкам с известным соответствующим флагом. Доли `recommend_for` и `recommend_against` могут пересекаться, строка входит в каждый знаменатель максимум один раз. Показывай знаменатели и исключения.
4. Сегментация: бренд, поверхность, режим, язык, география, когорта, стадия. Поверхности не сливай в одну долю.
5. Показатели по ответам и по промптам обозначай раздельно. Одно число «доля голоса» не выдавай: упоминания, рекомендации и формулировка — отдельно.
6. Агрегация по теме покупки: несколько промптов одной темы («лучший auth API», «SSO для SaaS») — одна тема. Для проигранных тем: открой источники, процитированные в пользу конкурентов; проверь, есть ли своя страница, которая должна выигрывать (content.md, refresh.md); исключи технический слой (technical.md); после переобхода повтори тот же портфель.

### 7. Динамика по промптам

- Ключ сравнения в каждом неизменном сегменте: ID и версия сценария, номер хода, ветка при наличии, ID и версия промпта, версия правил классификации. ID сессии идентифицирует повтор; разные сессии допустимы.
- Одинаковый текст уточнения отдельно и внутри цепочки — разные ключи, не сравнивай.
- Сравнивай на ключах с ненулевым знаменателем в обоих периодах. Сначала доля внутри ключа по формуле одного периода, затем среднее долей с равным весом каждого ключа.
- Показывай изменение в процентных пунктах, число общих ключей, число валидных повторов, исключения.
- Нет общих ключей — срезы периодов без вывода о динамике. Новый или изменённый ключ открывает базовую линию.
- Пример: два неизменных промпта, A всегда с рекомендацией, B никогда; повторов в октябре 3/9, в ноябре 9/3. Доля в обоих периодах 50% (среднее 100% и 0%), изменение 0 п. п. Пул повторов дал бы 25% → 75% — это ошибка.
- Пример: 2/10 → 8/10, но восемь промптов заменены брендовыми, два общих не изменились. Динамика на двух общих ключах равна нулю; восемь новых получают базовую линию.

### 8. Лестница обнаружения

Прочитан → процитирован → упомянут → рекомендован; рядом — «рекомендован против».

| Ступень | Где видна |
|---|---|
| Прочитан | Почти не видна; косвенно — логи ботов (technical.md, measure.md) |
| Процитирован | `citation` в журнале, списки источников |
| Упомянут | `mention` |
| Рекомендован / против | `recommend_for` / `recommend_against` с формулировкой |

Рост цитат при плоской доле рекомендаций — диагностируемый разрыв: внешние источники не подтверждают контент (offpage.md). Отчёт показывает ступени отдельно.

**Риск самопромо-листиклов.** Собственный рейтинг «лучшие {категория}» с брендом на первом месте модель может использовать как источник о категории: извлечь конкурентов и критерии, а рекомендацию построить по внешнему консенсусу. Для бренда вне консенсуса такой гайд может давать цитату (ghost) без рекомендации и описывать конкурентов. Количественные оценки эффекта (исследование Lily Ray / Amsive, 2026) — требует проверки по evidence.md. Действие: проверь в журнале пару ghost + `recommend_for=false` на промптах, где процитирован свой листикл. Альтернатива самоназначенному первому месту — назвать лидера категории, честно описать его сильные стороны и показать конкретные случаи, где продукт сильнее (content.md). Подлинно полезные гайды допустимы на любой стадии; ожидание — цитата и рамка категории, не шорт-лист.

### 9. Фоновые запросы ChatGPT

Для портфеля и покрытия подтем можно извлечь реальные фоновые запросы ChatGPT с поиском: запусти промпт, DevTools → Network, обнови беседу (ID после `/c/`), найди ответ с данными беседы и поищи в нём `queries`. Метод — публично распространённое наблюдение (AI format-volatility.md, август 2026); интерфейс и поле требуют проверки на дату использования. Извлечённые запросы — данные для портфеля и content.md (подвопросы, страницы-владельцы фактов), а не основание массово публиковать страницу на каждый запрос. Запросы `site:` к сторонним площадкам — вход для offpage.md.

### 10. Утилита и импорт

`scripts/visibility_tracker.py` ведёт журнал по контракту выше. Путь обязателен, в cwd по умолчанию не пишет, исходные файлы не перезаписывает. Интерфейс:

```bash
python3 scripts/visibility_tracker.py init   --path <журнал>
python3 scripts/visibility_tracker.py add    --path <журнал> <поля строки>
python3 scripts/visibility_tracker.py report --path <журнал>
python3 scripts/visibility_tracker.py import --path <журнал> <старый CSV или JSON>
```

Точные флаги полей — `--help` скрипта. Скрипт используй после валидации его версии; иначе ручная таблица с теми же полями.

Импорт старых данных — по разделу «Совместимость и миграция» (контракт миграции `scripts/visibility_tracker.py`, допуск импортированных наблюдений):

- Исходный файл и строки неизменны; повторный импорт без дублей по идентификатору файла и строки.
- Все записи `citation_tracker.py` идут в карантин: `provenance=unverified`, все четыре флага `unknown`, включая статусы `ghost`, `neither` и `both` (явный и подставленный по умолчанию неразличимы). `status` сам по себе метрику не даёт; сходство с демонстрационным текстом не классифицирует строку.
- Подтверждение по сохранённому ответу, ссылкам или выдержке с метаданными, либо явному подтверждению владельца по строкам: реальные — `provenance=observed`, демонстрационные (`sample`) — `provenance=demo`, вне метрик. Заполняй только подтверждённые флаги. Подтверждённое происхождение без подтверждённого исхода оставляет `unknown`.
- Старый CSV: исторический `recommended` сохраняется; подтверждённое `y` → `recommend_for=true`; `n` и пусто — сверка ответа; `recommend_against=unknown` до независимого подтверждения. Известная целая `position`, привязанная к подтверждённой рекомендации, переносится.
- Строки без полей ключа сравнения — архив ограниченного охвата, в динамику не входят.
- Отчёт импорта: входное число строк, реальные, демонстрационные, ожидающие проверки, исключения из каждого знаменателя.

### 11. Передача

- Проверяемые факты из ответов, ошибки и основания `recommend_against` — entity.md (журнал утверждений).
- Независимые возражения, процитированные сторонние источники, запросы `site:` — offpage.md.
- Пробелы страниц и подтемы — content.md. Ghost на своём контенте — content.md (явная связь бренда с собственным фактом).
- Показатели видимости для отчёта по каналам — measure.md.
- Объяснение дрейфа поверхности — evidence.md, platforms.md.

## Выход

- Вопрос измерения, версия портфеля, когорты и стадии, поверхности с режимом, дата, число повторов.
- Протокол прогона и таблица журнала (заполненная наблюдениями или пустая).
- Доли по флагам и both/ghost/mention-only/neither со знаменателями, исключениями и сегментами; раздельно по ответам и по промптам.
- Динамика — только по контракту раздела 7: п. п., число общих ключей, повторы, исключения; иначе срезы.
- Лестница, соседи, классы источников, формулировки отношения, передачи в entity/offpage.
- Непроверенные поверхности со статусом «не проверено».

Не возвращать: сгенерированные или додуманные ответы моделей; доли, слитые по поверхностям; рост по заменённым промптам или по перевесу повторов; флаги из импорта без подтверждения; провенанс, выведенный из `status`; «доля голоса» одним числом; гарантии появления.
