# technical

## Вход

- Обязательно: URL, домен или сохранённые HTML / robots.txt / заголовки ответа.
- Целевая поверхность (поисковая система или AI-поверхность) и назначение URL: индексировать или нет. Без поверхности по умолчанию проверяй основную поисковую систему рынка из входа и помечай выбор.
- Опционально: рендер страницы, проверенные логи сервера/WAF/CDN, отчёты GSC, Bing Webmaster, Яндекс Вебмастера, список URL от владельца, сценарий агентского действия.
- Объём выборки, бюджет запросов и стоп-условия задаёт SKILL.md («Проверки и решения»). Здесь они не повторяются.

## Процедура

Все наблюдения сохраняй по паре `URL × поверхность` с датой, запросом и выдержкой ответа. Отсутствие данных даёт unknown, а не pass или fail.

### 1. HTTP и редиректы

1. Запроси каждый URL выборки как типичный клиент (браузерный UA). Сохрани цепочку редиректов, финальный URL, код, признаки CDN.
2. Финальный ответ не 2xx после допустимых редиректов → находка `http_status`. URL исключается из знаменателей остальных постраничных проверок (audit.md).
3. Сетевой сбой, таймаут, TLS-ошибка → unknown, не ошибка сайта.
4. Варианты одного адреса (http/https, www/без www, старые домены) → проверь, что все ведут одним 301 на один основной адрес и canonical на нём согласован.
5. Отсутствующий путь отвечает 200 со страницей «ничего не найдено» → мягкий 404, эвристика без балла. На SPA проверь несколько заведомо несуществующих путей.
6. Троттлинг отдаётся страницей-челленджем вместо 429 с `Retry-After` → эвристика без балла.

### 2. robots.txt

1. Получи `/robots.txt` на каждом хосте выборки. Различай исходы: 200 с текстом, 403, 404, 429, 5xx, сетевая ошибка. Последствия 4xx и 5xx для конкретного бота сверяй с его документацией (по Plugin 4: Google трактует 4xx, кроме 429, как отсутствие ограничений, а 5xx как остановку обхода, требует проверки по Google Search Central). Сетевая ошибка без иных данных → политика unknown, не allow.
2. Разбор групп (RFC 9309):
   - подряд идущие строки `User-agent` образуют одну группу. Правило после них действует на каждого агента группы, а не только на последнего;
   - бот подчиняется только группе со своим токеном. Именованная группа заменяет для него все правила `User-agent: *`. Fallback на `*` действует только при отсутствии именованной группы;
   - `*` в пути совпадает с любой последовательностью символов, `$` привязывает конец пути;
   - из совпавших правил побеждает самое специфичное (самый длинный путь). При равной длине `Allow` и `Disallow` побеждает `Allow`;
   - пустой `Disallow:` ничего не запрещает.
3. Проверяй путь каждого URL выборки, а не только `/`. Запрет корня не доказывает блокировку каждого пути без разбора правил.
4. Для каждого агента из матрицы platforms.md, относящегося к целевой поверхности, выведи `robots_policy`: allow / block / unknown. Роль агента (search, training, user-initiated, управление использованием) бери из platforms.md. Блок training-агента сам по себе не является выпадением из поиска.
5. При проектировании правил:
   - новая именованная группа теряет запреты из `*` (например `/private/`). Перенеси нужные `Disallow` в новую группу явно и проверь путь заново;
   - по умолчанию держи общую группу `*` и добавляй именованные группы только для намеренных исключений. Список разрешённых имён без `*` исключает неизвестных агентов. Wildcard не является рецептом для каждого сайта: решение по владельцу и его ограничениям;
   - пользовательские агенты могут не учитывать robots.txt по заявлению вендора (platforms.md). Ограничение для них проверяй по документации, а не по файлу.
6. Изменение robots выдавай предложением по правилу подтверждения URL (SKILL.md, «Проверки и решения»). Копию правила не храни здесь.

### 3. WAF, CDN и диагностическая UA-проба

1. Запроси ограниченную выборку (главная и один URL на шаблон) с UA целевого поискового бота. Это диагностическая проба: она даёт гипотезу, а не факт визита бота.
2. Клиент 200, проба 403/429/503/челлендж → находка «требует проверки по логам» без балла. В `http_status` не входит. Причина возможна в защите от поддельных ботов: запрос с UA поисковика с чужого IP часто отсекается.
3. Подтверждённый отказ подлинному боту требует: верификации бота по политике вендора (опубликованные диапазоны IP, обратный DNS, подписи Web Bot Auth, если вендор их документирует) и журнала WAF/сервера с датой, URL и решением о блокировке, либо авторизованного диагностического отчёта платформы. Только тогда отказ учитывается в `search_crawl_access`.
4. Настройки CDN по умолчанию (например, блокировка AI-краулеров в Cloudflare) требуют проверки тарифа, зоны, даты подключения и фактической конфигурации. Не выводи их из названия провайдера.
5. Не обходи WAF и не подбирай UA ради доступа. Все URL выборки недоступны типичному клиенту → прогон недействителен (SKILL.md).

### 4. Логи

1. Читай только предоставленные логи. Совпадение строки UA и подтверждённая идентичность — разные поля. Поддельный UA не засчитывай как визит.
2. Агенты пользовательских открытий (`ChatGPT-User`, `Claude-User`, `Perplexity-User`) показывают страницы, которые открывают по запросам людей. Открытие агентом не является переходом пользователя: атрибуция в measure.md.
3. Много 403/429 у подтверждённого бота → кандидат на подтверждённый отказ (шаг 3.3).

### 5. meta robots и X-Robots-Tag

1. Для пары `URL × поверхность` фиксируй отдельно: директиву в `<meta name="robots">` или в meta для конкретного бота, директиву в `X-Robots-Tag`, может ли целевой бот прочитать представление, намерение владельца, фактическую индексацию.
2. Чтение разрешено, URL предназначен для индексации, есть noindex → `index_directive` fail. Директивы нет → pass.
3. Чтение заблокировано robots или подтверждённым отказом → чтение «заблокировано», применение noindex «не подтверждено», `index_directive` неприменима к оценке. Блокировка учитывается в `search_crawl_access`.
4. Без подтверждённых различий представлений допустимо оценить директиву по ответу типичному клиенту с пометкой «допущение». Известны разные представления, а ответ для поверхности установить нельзя → unknown.
5. Директива в ответе клиенту не подтверждает её обработку ботом и исчезновение URL из выдачи.

### 6. Проверка применения noindex

1. На вопрос «сработал ли noindex?» сверь статус URL и дату последнего обхода в отчёте целевой системы (например, инспекция URL) с датой установки директивы.
2. Обход запрещён и URL уже в индексе → «проиндексирован по данным на <дата>, текущую директиву бот не может прочитать».
3. Нет актуальной инспекции → статус индексации «не проверено».
4. Публичный URL надо убрать из индекса → предложи открыть целевому боту чтение сохраняемого noindex и проверить статус после повторного обхода. Перед предложением сверь поддержку директивы платформой и намерение владельца.
5. Приватный URL → сохраняй ограничение доступа, проверь штатный механизм удаления у площадки.
6. Изменения только по правилу подтверждения URL (SKILL.md).

### 7. canonical

1. Разрешай `rel=canonical` от финального URL с учётом `<base href>`. Не склеивай схемы и хосты без подтверждённого соответствия.
2. canonical указывает на другой адрес без подтверждённого дубля или пагинации → `canonical_target` fail. Осознанный cross-canonical исключи с причиной.
3. Сверь canonical с редиректами (шаг 1.4), sitemap и hreflang: все должны указывать на один основной адрес.

### 8. sitemap

1. Ищи sitemap в строках `Sitemap:` robots.txt, затем по известным путям. Поддерживай gzip и индексы sitemap с ограничением глубины, размера, числа запросов и защитой от циклов.
2. Ни один sitemap не найден при успешных запросах → `sitemap_discovery` fail. Сетевой сбой → unknown, не «нет sitemap».
3. URL в sitemap с не 2xx, noindex или canonical на другой адрес → находка о гигиене sitemap без отдельного балла.
4. Для аудита одной страницы проверка неприменима.

### 9. Внутренние ссылки

1. Ссылки считай только из `<a href>` в raw HTML. Навигация, собираемая скриптом, для обхода отсутствует.
2. Достижимость (`internal_reachability`) оценивай только при полном фронтире заявленной глубины. Иначе «неприменима: фронтир неполный». Не объявляй сиротами страницы, которые не попали в обход.
3. Пагинация обычными ссылками. Фильтры каталога и их индексируемость передай в ecommerce.md.

### 10. raw HTML и рендер

1. Сравни основное содержимое (текст, цены, характеристики, ответ) в raw HTML и в рендере. Решение о JS-зависимости по разнице основного содержимого, не по счётчику слов.
2. Есть в raw → pass. Нет в raw, есть в рендере → `main_content_raw` fail. Рендера нет и в raw пусто → unknown, покрытие неполное.
3. Тип страницы определяй по содержимому и метаданным, без обязательных сегментов пути вроде `/blog/`.
4. Варианты исправления по убыванию надёжности: статическая генерация, SSR, гибрид, статический запасной HTML для ключевых страниц. Динамический рендеринг только для ботов не предлагай как основное решение.
5. JSON-LD, вставляемый тег-менеджером, отсутствует в raw. Критичные факты дублируй видимым текстом. Правила разметки в content.md.
6. Стены перед контентом (выбор языка или города, cookie, логин, pop-up поверх текста) проверяй без cookie. Это эвристика без балла.

### 11. Язык, локаль, hreflang

1. Язык и страна — разные измерения: испанский в Мексике, испанский в Испании и английский в Мексике — три конфигурации.
2. На каждой локали проверь `lang` у `<html>`, язык основного содержимого, локальные факты (цена, валюта, наличие, политика, часы поддержки). Неверная локальная цена — находка высокого приоритета, сверка фактов в entity.md.
3. hreflang: проверь, что каждая альтернатива отвечает 2xx, индексируема, совпадает со своим canonical и ссылается обратно. Синтаксис и поддержку сверяй с документацией целевой поисковой системы (Google Search Central; для Яндекса карточка в platforms.md требует проверки).
4. Различай разрывы: перевода (страница есть, но не на этом языке), информации (факта нет локально), сущности (локальные профили расходятся). Последние два передай в content.md и entity.md.
5. Не рекомендуй `/en/`-зеркало как универсальный способ увеличить цитирование: тезис в evidence.md, требует проверки.
6. Отчитывайся отдельно по каждому языку, стране и поверхности до свёртки.

### 12. Агентская доступность (только по запросу)

1. Зафиксируй сценарий: цель агента (найти цену, сравнить план, отправить форму, записаться), стартовый URL, ожидаемый результат.
2. Шаги сценария проверяй по:
   - основное содержимое и цена в raw HTML как текст, не картинкой, калькулятором или формой продаж;
   - реальные коды ответа (шаг 1);
   - дерево доступности: landmarks `banner`, `main`, `navigation`, `contentinfo`; у кнопок, ссылок и полей формы различимые доступные имена; роли нативных элементов вместо `div` с обработчиком; таблицы с заголовками строк и столбцов; содержательный alt у смысловых изображений, `alt=""` у декоративных допустим;
   - ключевые действия (регистрация, цена, демо, контакт) работают без JS-only потока и возвращают проверяемое подтверждение;
   - отзывы, рейтинги и логотипы клиентов как текст, а не только в изображении или виджете.
3. Инструмент снимка дерева: Chrome DevTools (панель Accessibility, полное дерево) или API автоматизации. API сверяй с документацией используемой версии: `page.accessibility.snapshot()` из исходника может отсутствовать в текущем Playwright, требует проверки.
4. Результат — пройден ли конкретный сценарий и на каком шаге сбой. Не обобщай на «готовность сайта для агентов».
5. MCP-сервер, WebMCP, AI Catalog, Markdown-зеркала: только по явному запросу, с проверкой текущей спецификации и поддержки у нужного клиента (platforms.md). Эффект на выбор агентом и цитирование требует проверки (evidence.md).

### 13. Машиночитаемые документы (только по явному запросу)

`llms.txt`, `llms-full.txt`, `/pricing.md`, OKF-бандл и Markdown-версии страниц — необязательные документы для конкретного потребителя с явной задачей. Влияние на ранжирование, цитирование и снижение галлюцинаций не доказано и требует проверки по документации вендора или воспроизводимому тесту (evidence.md). Google заявляет, что для его AI-функций специальные файлы не нужны (platforms.md).

1. На вопрос «нужен ли файл» отвечай коротко: доказанность влияния отдельно от формата. Обход сайта ради ответа не запускай.
2. Файл создаётся только из реальных данных пользователя: реальные URL с ответом 2xx, подтверждённые факты, актуальные цены. Не подставляй примерные бренды, сертификаты, цифры или URL. Нет данных → пустые места с пометкой «нужны данные».
3. Формат и валидатор бери из текущей спецификации файла (`llms.txt` — llmstxt.org; OKF — спецификация в репозитории `GoogleCloudPlatform/knowledge-catalog`, версия на дату проверки). `/pricing.md` стандартом не является: единицы (месяц/год, за место/фикс), лимиты и состав тарифов должны совпадать с видимой страницей цен.
4. Файл в корне домена, отвечает 2xx, не запрещён в robots.txt, на него ведёт ссылка со страниц, которые уже читают (подвал, `<link>` в head).
5. Назначь владельца обновления. Устаревший документ с ценами хуже его отсутствия.
6. OKF создавался для обмена метаданными каталогов данных. Использование для маркетингового сайта — переосмысление формата. Не обещай обнаружения бандла AI-поисковиками.

### 14. Изменения индексации и адресации

noindex, canonical, redirect, запрет в robots и удаление страниц выдавай только предложением по правилу подтверждения URL в SKILL.md («Проверки и решения»). Не меняй SEO-элементы, о которых не просили.

## Выход

- Отчёт по `URL × поверхность`: финальный URL и цепочка, код для клиента, `robots_policy`, код пробы, `verified_access` (allowed / blocked / unknown), директивы и возможность их чтения, canonical, raw/render, индексация с датой и источником или «не проверено».
- Находки в формате SKILL.md (`приоритет | проблема | объект и доказательство | действие | проверка результата`). Подтверждённая непреднамеренная блокировка релевантного доступа на ключевых URL идёт первой.
- Отдельно: находки «требует проверки по логам», эвристики без баллов, непроверенные области (нет GSC / Bing Webmaster / Яндекс Вебмастера / логов / рендера).
- Предложения изменений — списком URL или правилом с числом URL и примерами.
- Не возвращать: балл без запроса оценки; UA-пробу как визит бота; вердикт по Яндексу или Алисе до сверки карточки; noindex как подтверждённую деиндексацию; «сирот» при неполном фронтире; шаблонные `llms.txt`/`pricing.md` с чужими данными.

## Проверки `tech-v1` и эвристики

Реестр, веса, применимость, потолки и сопоставимость снимков принадлежат audit.md («Техническая оценка»). technical собирает для них наблюдения.

| check_id | Уровень | Наблюдение technical |
|---|---|---|
| `http_status` | critical | шаг 1 |
| `search_crawl_access` | critical | шаги 2–3 |
| `index_directive` | critical | шаг 5 |
| `canonical_target` | high | шаг 7 |
| `main_content_raw` | high | шаг 10 |
| `sitemap_discovery` | medium | шаг 8 |
| `internal_reachability` | medium, опциональная | шаг 9 |

Эвристики выводятся находками без баллов: мягкий 404, 429 без `Retry-After`, стены и pop-up перед контентом, JSON-LD только из тег-менеджера, отсутствие `lang`, формат изображений, отсутствие `Sitemap:` в robots.txt, URL в sitemap с не 2xx/noindex/чужим canonical, размер HTML (порог 4 МБ требует проверки, evidence.md). Title, H1, ответ после H1, вопросные H2, alt, таблицы, schema, meta description и `dateModified` — эвристики content.md. Core Web Vitals, миграции и ссылочный профиль — профильному навыку (SKILL.md, Background).
